# ADR 0029：前端选地报告优先级队列

## 状态

已接受

## 背景

下载机同时承载定时总览、普通页面数据刷新和前端发起的选地报告申请。报告申请需要先完成遥感、天气、土壤数据拉取，再生成单地块报告；如果仅按提交时间排队，后台任务会把用户刚发起的报告长时间挡住。系统目前同时存在 API `work_items` 认领队列和下载机 Celery Redis 队列，优先级必须贯穿两层，并且不能让 fan-out 子任务降级。

## 决策

业务优先级统一为 0 到 9，数值越大越优先：

- 9：前端一键选地报告，包括批量报告的共享遥感任务、每块地的天气/土壤拉取和报告 follow-up。
- 5：普通页面触发的单独遥感、天气、土壤或建档任务。
- 0：定时总览及其他后台任务。

API 只允许服务端路由决定优先级，不接受客户端在 payload 中伪造 `priority`。`work_items` 继续按优先级降序、创建时间升序认领；MQ `TaskMessage` 携带业务优先级，MQ consumer 和 claim agent 派发 Celery 时统一传递。

Celery 使用 Redis transport 的优先级 list，并将业务优先级转换为 Redis 出队优先级：Redis 数值越小越先出队，因此业务 9 映射到 Celery 1，业务 5 映射到 4，业务 0 映射到 9。未显式标注的历史/定时任务由发布信号归入后台优先级。worker 预取倍数设为 1，任务内部继续派发的子任务继承父任务优先级。

## 结果与边界

- 优先级只影响等待中的任务；已经在 worker 执行的任务不会被中断。
- CloudAMQP 继续作为兼容性的外层传输，不改动已有队列声明；consumer 取到消息后，优先级在下载机本地 Redis 队列生效。
- 高优先级报告仍受并发数、外部遥感服务限流和单任务超时约束，不承诺绕过正在运行的下载。
- 通过统一转换函数避免 Redis 与 RabbitMQ 的数值方向差异误用；当前部署 broker 是 Redis，若更换 broker 必须重新验证映射。

## 未采用的方案

- 不让前端直接传数值优先级：这会让普通接口调用方可以挤占报告专用队列。
- 不为报告另建一套 Celery 队列：报告的遥感、天气、土壤和 follow-up 需要共享 worker 资源与统一排序，拆队列会引入跨队列饥饿和状态跟踪复杂度。
