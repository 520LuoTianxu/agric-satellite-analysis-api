# 总览预聚合 OSS 批次交换设计

## 背景

`overview-refresh` 原来在 API 请求内遍历所有地块、读取 S1/S2 观测和像元 JSON，
然后直接计算并写入 `overview_stats_daily`。地块数量变大后，HTTP 请求会长时间占用
API 数据库连接，容易被网关判定为 504；响应也不适合携带大字段。

## 方案

1. API 按 `land_id` 游标和 `land_batch_size` 分批查询，默认每批 10 个地块。
2. 每批原始观测写入 `overview/preagg/input/` 下的 OSS JSON，接口只返回 OSS 签名地址、
   SHA-256、字节数和下一页游标。
3. 下载机从 OSS 下载并校验批次，在本地完成干旱、洪涝、弱长势和行政区汇总；原始像元
   不进入 HTTP body，也不在下载机长期缓存。
4. 下载机把紧凑的区域结果写入 `overview/preagg/output/`，API 只接收结果对象 key，
   校验结果模型后写入 `overview_stats_daily`。

## 失败处理和取舍

- OSS 输入包使用字节数和 SHA-256 校验，校验失败时任务失败并保留批次，便于重试和排查。
- 游标没有前进、结果包格式不合法或 OSS 读取失败时不写缓存，避免生成不完整总览。
- 任务重试会重新读取批次；缓存表使用原有唯一键 upsert，重复提交不会产生多份统计。
- API 仍负责访问 PostgreSQL 和生成输入包，保持下载机不直连数据库的安全边界。
- OSS 会产生临时输入/输出对象，后续应增加生命周期清理策略；当前先保留对象以便审计和失败重试。
- 默认批次为 10，单批更小会减少单次内存和请求耗时，但会增加 API/OSS 往返次数。
